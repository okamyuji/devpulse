## 1. 目的と背景

複数のAIエージェント（Claude Code、Codex、Kimi）をcmuxのworkspaceや別ターミナルで並列に走らせる運用が日常化した結果、「いまどこで、どのエージェントが、どの作業ツリーに対して、動いているのか停まっているのか」を一望する手段がないという問題が生じています。各エージェントの画面は自分のセッションしか表示せず、cmuxのサイドバーはcmux内で起動したものしか扱いません。

DevPulseはローカル開発環境の状態を一画面に集約するTUIであり、この観測をひとつのパネルとして加えることは製品コンセプトの自然な延長です。

## 2. 成功条件

本機能の成功条件を次のとおり定義します。

> cmux、tmux、dmux、DevFleet、エージェント内サブエージェントを横断し、実行場所、作業ツリー（worktree）、活動状態、リソース競合を統一表示するローカル観測パネルとして機能すること。

この成功条件は本機能の最終像を定めるものです。MVPは3節で定める範囲によってその第一歩を実施し、横断対象は段階的に広げます。したがってMVPの完了時点では、成功条件のうち7.3節に定める取得元4種（cmuxのCLI、Claude CodeのCLI、Kimiのセッションメタデータ、プロセス情報）で観測できる範囲までの達成を判定対象とします。

「各エージェントのセッションデータベースを横断表示すること」は成功条件ではありません。単にcmuxのworkspace一覧をDevPulseへ再表示するだけでは、cmux内蔵のサイドバーと重複して価値が薄いためです。価値の中心は次の観点の掛け合わせにあります。

1. orchestrator横断。cmuxのsurface、tmuxやdmuxのpane、Claudeのバックグラウンドエージェント、Codexのサブエージェントスレッド、DevFleetのmissionを同じ行モデルへ正規化して1画面に載せます。
2. worktree競合の検出。複数のエージェントが同一リポジトリ系列（同一のgit common directoryを共有するworktree群）で同時に作業している状況を警告します。この状況は各エージェントの単体画面からは把握しにくく、二重編集や競合の予防に直接効きます。
3. 無活動、失敗、孤児化の検出。プロセスは存在するのにイベントが途絶えているセッション、orchestrator上はrunningなのに子プロセスが消えているセッション、失敗したままpaneだけ残っているセッションを見つけます。

## 3. スコープ

### 3.1 MVPで実施すること

- 読み取り専用のcollectorをCLIサブコマンドとして実装し、エージェントセッション一覧をJSONで出力すること
- 取得元は実稼働を確認済みの範囲に限定すること（cmuxのCLI、Claude Codeのエージェント一覧CLI、Kimiの文書化済みセッションメタデータ、プロセス情報のフォールバック）
- collectorの検証後に、TUIのProcessesパネルへ切り替え式のビューとして統合すること
- PID、cwd、worktreeの対応付けと、同一リポジトリ系列の並行作業警告を実装すること
- 静穏時間（最終イベントからの経過時間）の表示を実装すること
- 取得元のいずれかが未インストールまたは停止していても、DevPulse全体は動作を継続すること

### 3.2 MVPで実施しないこと

- セッション本文やプロンプト内容の表示
- エージェントの停止、再開、メッセージ送信などの操作（本機能は読み取り専用とします）
- 非公開SQLiteの直接解析
- 「詰まっている」ことの自動断定（状態分類の節で述べるとおり、静穏は事実として表示し解釈はしません）
- DevFleetのmission操作
- エージェント成果物の自動マージ
- tmux、dmux、DevFleet、Codexのapp-serverを取得元へ加えること（取得元の節で述べる理由により第2段階へ送ります）
- 5パネル可変レイアウト（UI統合の節で述べるとおり第2段階へ送ります）

## 4. 全体構成

本機能は取得層、正規化層、表示層で構成します。

1. 取得層は複数の取得元アダプタの集合です。各アダプタは共通インターフェース（trait）を実装し、失敗しても他のアダプタとDevPulse本体に影響を与えません。DevPulse既存のポート取得やプロセス取得と同じ抽象化方針です。
2. 正規化層は各取得元の生データを統一行モデル（データモデルの節で定義）へ変換し、PIDとcwdの照合で同一セッションの重複を統合します。cmuxに見えるセッションとプロセス走査で見えるセッションは排他ではなく合流させます。cmux外で起動したセッションはプロセス走査でしか見えないためです。
3. 表示層はJSON出力（collector）とTUIビューの2形態です。同じ正規化済みデータを両方が使います。

最初の成果物はTUIではなくcollectorとします。JSONの出力内容で「cmux上の各エージェントとworktreeが正しく結び付くこと」を先に実証してから、TUIへ載せます。UIの手戻りを避けるための順序です。

## 5. データモデル

統一行モデル（エージェントセッション1件分）は次の属性で構成します。基本設計として意味を定義し、型の詳細は詳細設計に委ねます。

| 属性 | 意味 |
|---|---|
| id | セッションの識別子 |
| agent | エージェント種別（Claude、Codex、Kimi、その他） |
| orchestrator | 実行環境の種別（cmux、tmux、dmux、DevFleet、プロセス内） |
| location | 実行場所（workspace、pane、surface、PIDなどの参照） |
| cwd | 作業ディレクトリ（取得できた場合のみ） |
| worktree | 対応するgit worktree（取得できた場合のみ） |
| git_common_dir | worktree共通ディレクトリ（競合判定に使用。取得手段は7.1節の補足で定める） |
| task_title | タスク名や作業名（取得できた場合のみ） |
| state | 状態分類の節で定義する状態 |
| state_source | 状態の根拠となった取得元 |
| confidence | 状態の確度（公開APIの報告か、間接的な推定かの区別） |
| last_activity_at | 最終活動時刻（取得できた場合のみ） |
| cpu_percent、memory_bytes | リソース使用量（プロセス情報から取得できた場合のみ） |
| child_agents | 配下のサブエージェント数（取得できた場合のみ） |

state_sourceとconfidenceは必須属性とします。たとえばCodexの公開APIがactiveと報告した場合と、ファイルの更新時刻が新しいだけの場合を、同じ確度として扱ってはならないためです。

## 6. 状態分類

「詰まっている」という断定を避け、観測事実と解釈を分離するため、状態は次のとおり分類します。

| 状態 | 定義 |
|---|---|
| running | 公開APIまたはCLIが実行中と報告している |
| waiting | 承認またはユーザー入力待ちと報告されている（この報告を返す取得元が確認できないセッションでは、推定でwaitingとせずunknownとして扱う） |
| idle | 公開APIまたはCLIがidleと報告している |
| quiet | イベントが一定時間ない（経過時間を併記する。例: quiet 8m） |
| failed | 公開APIまたはCLIが失敗と報告している |
| orphaned | 親（workspaceやsurface、pane、mission）とプロセスの対応が不整合である（MVPではcmuxのworkspaceやsurfaceおよび親プロセスとの対応だけを判定し、tmuxやdmuxのpane照合とmission照合は各取得元と同じ第2段階とする） |
| unknown | 確実な判定材料がない |

quietは事実の表示であって故障の断定ではありません。長時間のテスト実行や思考中でもイベントは途絶えるため、解釈は利用者に委ねます。

## 7. 取得元と優先順位

### 7.1 優先順位

保守コストを抑えるため、非公開形式への依存を避け、次の順序で取得します。

| 優先度 | 取得元の種類 | 例 |
|---|---|---|
| 1 | 公開APIまたは公開CLI | cmuxのtree、workspace status、events。Claude Codeのエージェント一覧CLI |
| 2 | プロセス情報 | PID、cwd、コマンド、CPU、メモリ、親子関係 |
| 3 | 公式に文書化されたローカル保存形式 | Kimiのセッションインデックスとセッションディレクトリ |
| 4 | 非公開SQLiteやJSONL | 利用者が明示的に有効化した場合だけのフォールバック。スキーマ不一致時は無効化してunsupported表示とする。3.2節の宣言どおりMVPでは実装せず第2段階とする |

worktreeとgit common directoryは、上表のどの取得元の出力にも含まれません。そのため、各セッションのcwdを起点にgitコマンドを呼び出して取得します。この照会は取得層のアダプタの一員として扱い、10節の縮退方針を同様に適用します（照会に失敗した場合、worktree関連の属性は欠落として扱います）。読み取り専用の用途に対して新規のライブラリ依存を増やさないため、ライブラリではなくコマンド呼び出しを採用します。なお、この照会の出力は呼び出し位置によって相対パスと絶対パスが混在することを実測で確認済みのため、8節の照合を含むすべての比較は絶対パスへ正規化した値で行います。

### 7.2 観測のためにサーバーを起動しない

Codexのapp-serverとKimiのローカルサーバーは公開APIを持ちますが、本環境での確認の結果、どちらも常時稼働のデーモンではありませんでした。読み取り専用の観測ツールが観測のためにデーモンを起動するのは自己矛盾であるため、次の規則を置きます。

> サーバー型の取得元は、既に稼働している場合だけ使用します。観測のために起動しません。稼働していない場合は優先度2以下の取得元へ落とします。

### 7.3 MVPの取得元

2026-07-18に本環境で実稼働を確認できた取得元だけをMVPに含めます。

| 取得元 | 確認済みの事実 |
|---|---|
| cmuxのCLI | v0.64.19が稼働中。tree、workspace list、events、capabilitiesの動作を確認済みで、eventsの出力にcwd、セッションID、発生時刻が含まれることも確認済み。公開CLI契約文書（cli-contract.md）を持つ。list-workspacesはlegacy aliasで通知行が出力へ混入するため、正式形のworkspace listを使う。workspace statusはtodo statusの表示用コマンドであり、セッション状態の取得には使わない（状態はtreeとeventsから得る） |
| Claude CodeのCLI | エージェント一覧をJSONで返すコマンドが動作し、id、cwd、種別、セッションID、名前、状態を返すことを確認済み |
| Kimiのセッションメタデータ | セッションディレクトリが実在し、ディレクトリ名に作業ツリー由来の名前が含まれることを確認済み。構造は公式資料に文書化されている |
| プロセス情報 | DevPulse既存のプロセス取得基盤（sysinfo）を流用する。cwdの取得は小規模な拡張が必要 |

tmux、dmux、DevFleet、Codexのapp-serverは、取得層のインターフェースに追加余地を残した上で第2段階とします。tmuxは本環境で現在稼働しておらず、Codexのapp-serverは実験的機能かつ非稼働のためです。取得元を増やすことより、少数の取得元で正規化と統合の正しさを実証することを優先します。

## 8. worktree競合の検出

同一リポジトリ系列に対する複数エージェントの同時作業を検出し、警告表示します。ここでの同一リポジトリ系列とは、同一のgit common directory（worktree群が共有する管理ディレクトリ）を持つworktree群のことです。別々のworktreeで作業していても、同じリポジトリ系列に属していれば警告の対象になります。判定にはcwdの一致ではなくcommon directoryの照合を使います。cwdが同じでも同一リポジトリ系列とは限らず、逆に異なるcwdが同じ系列に属する場合もあるためです。

## 9. UI統合の方針

TUIへの統合は、既存のProcessesパネルにキー操作で切り替える別ビューとして行います。Processesビューとエージェントセッションビューを同じパネル領域で切り替える方式です。

5枚目の独立パネルを追加する案は第2段階とします。現行のDevPulseはパネル数が4で固定されているためです。4を前提とする実装はパネル列挙型、レイアウト計算、パネル状態配列に加えて、描画の呼び出しとパネル選択のキー操作処理にも及んでおり、5パネル化はUI基盤の広い変更を伴います。切り替えビュー方式ならこの変更を避けて小さく安全に導入できます。

ただし切り替えビューにも設計上の前提があります。現行実装はパネル1枚につきデータ1系列（選択位置、ソート条件、データ長の参照が1対1）を前提としているため、Processes枠に2つ目のビューを載せる際は、選択位置、ソート条件、データ長の参照をビューごとに分離して保持し、この前提に依存する処理をビュー単位で分岐させます。分岐の具体的な設計は詳細設計で扱います。

表示列は状態、エージェント、タスク名、実行場所、worktree、静穏時間、CPU、メモリを基本とします。詳細な列幅や配色は詳細設計で扱います。

## 10. エラー処理と縮退の方針

- 各取得元アダプタの失敗は該当取得元の欠落として扱い、他の取得元と本体の動作を止めません
- 取得元が使えない場合、その取得元由来の属性は「取得できなかった」ことが分かる表示にします。推定値で埋めません
- エージェントが未インストール、API停止、権限不足のいずれでも、DevPulse全体は起動と表示を継続します
- 状態の確度が下がる縮退（公開APIが使えずプロセス情報だけになる場合など）では、confidenceの低下を表示に反映します

## 11. 決定表

本設計で確定した主要な決定は次のとおりです。

| 決定事項 | 検討した選択肢 | 採用 | 理由 |
|---|---|---|---|
| 最初の成果物 | TUI先行、collector先行 | collector先行 | JSONで結び付きの正しさを先に実証し、UIの手戻りを避けるため |
| TUI統合方式 | 5パネル化、Processesパネル切り替えビュー | 切り替えビュー | 4パネル固定のUI基盤変更を避け、小さく安全に導入するため |
| 取得元の第一候補 | 非公開DB解析、公開CLIとAPI | 公開CLIとAPI | cmuxは公開CLI契約文書を持ち、非公開スキーマより追従コストが低いため |
| サーバー型取得元の扱い | 観測時に起動、稼働時のみ使用 | 稼働時のみ使用 | 読み取り専用の観測ツールが対象を起動するのは自己矛盾のため |
| セッションの統合方式 | 取得元ごとに別表示、PIDとcwdで照合し統合 | 照合し統合 | cmux外のセッションはプロセス走査でしか見えず、合流が必要なため |
| worktree判定 | cwd一致、git common directory照合 | git common directory照合 | cwd一致では誤判定が生じるため |
| 操作機能 | 読み取り専用、停止や再開の操作を含める | 読み取り専用 | MVPの破壊リスクを避けるため。既存パネルの操作系とは切り離す |
| 状態の断定 | 無活動を詰まりと表示、事実と解釈を分離 | 分離 | 長時間テストや思考中との区別が観測からは付かないため |
| worktree情報の取得手段 | gitライブラリの新規依存、gitコマンド呼び出し | gitコマンド呼び出し | 読み取り専用の用途に対して新規依存を避けるため（現行コードベースにgit関連の依存は存在しない） |

## 12. リスクと保守方針

| リスク | 対応方針 |
|---|---|
| cmuxのCLI出力仕様の変化 | 公開契約文書との差分で検知します。アダプタ単位で無効化できる構造とします |
| Claude CodeのCLI出力仕様の変化 | 同上。取得失敗時はプロセス情報へ縮退します |
| Kimiのメタデータ構造の変化 | 公式資料に文書化された範囲だけを読みます。不一致時はunsupported表示とします |
| 同一プロセス内サブエージェントの不可視性 | 公開された取得経路がない限り個別表示できない場合があることを仕様として明記します |
| 取得元の増加による保守負担 | 取得元の追加はアダプタ1個の追加に閉じ、正規化層と表示層に影響しない構造を保ちます |

## 13. 機能拡張として考えられる内容

第2段階以降で足す余地がある内容です。実施を確約するものではありません。

- tmux、dmux、DevFleet、Codexのapp-serverの取得元アダプタ
- 5パネル可変レイアウトへのUI基盤変更と、エージェントセッションの常時表示
- cmuxのeventsストリームを使ったプッシュ型の画面更新
- Windowsなどcmuxが存在しない環境向けの取得元構成
